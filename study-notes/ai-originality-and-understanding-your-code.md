# AI, Originality & Understanding What You Build (explained simply)

The professor's observations on what AI actually changes in software development. Builds on [ai-assisted-development-and-vibe-coding](ai-assisted-development-and-vibe-coding.md) and [project-presentation-and-technical-qa](project-presentation-and-technical-qa.md).

## What changes and what doesn't

| Gets easier | Stays hard |
|---|---|
| Producing good code | Understanding it |
| Producing documentation | Knowing whether it is correct |
| Getting to a first version quickly | Maintaining, extending, and defending it |

> You can use code immediately only if you already understand it.

If you don't, you spend the same time later working out what it does and whether it does it correctly. The speed advantage disappears the moment someone asks *why* it is structured that way, as in the technical Q&A.

## Point AI at problems that really exist

Cloning something already online, even if AI does it faster, builds nothing new: **a clone built faster is still a clone.** Originality comes from a specific problem, not novel technology. For the list matching project, the justification is the real-world need: reconciling two collections (data reconciliation, schema mapping, plagiarism detection) and seeing the matches instead of scanning text ([set-intersection-and-arrow-drawing](set-intersection-and-arrow-drawing.md), [list-matching-project-overview](list-matching-project-overview.md)). Define the problem and the decisions first; let AI help build them.

## Creativity: create curiosity, don't explain everything

A project that makes someone ask "how did they build this?" is more compelling than one that front-loads a walkthrough of every feature. Over-explaining is a common instinct in technical work and usually the wrong one. (Balance this with the README: the README still needs what it is and how to run it, see [readme-vs-wiki-documentation](readme-vs-wiki-documentation.md).)

## Authorship

If an AI assistant is a named contributor on a project submitted under your name, that is a different question from simply using AI help. Be clear about what you can explain and what you own ([github-repository-grading-criteria](github-repository-grading-criteria.md)).

**Open question:** at what point does AI assistance make a project yours versus the AI's? A working test: could you explain every decision and extend it without the AI?

## Key takeaway
> AI makes producing code easier, not understanding it. Use it on real problems, make sure you can explain what you built, and aim to create curiosity rather than explain everything.
