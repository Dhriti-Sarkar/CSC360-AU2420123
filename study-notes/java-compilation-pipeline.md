# Java Compilation Pipeline & Git Hygiene (explained simply)

## The full journey: from .java to .jar

This traces exactly what happens every time you build your project, step by step:

1. **`.java` file** — this is the plain, human-readable source code you actually write (like `App.java` in your square demo).
2. **`javac` (the Java compiler)** — takes that `.java` file and translates it into something the computer can actually run.
3. **`.class` file** — this is the output of `javac`: a compact binary file containing **bytecode**. This isn't your original readable code anymore — it's a structured, low-level format (made up of "opcodes" — individual instruction codes — and a "constant pool," a lookup table of values used by the program) that the **Java Virtual Machine (JVM)** knows how to execute directly.
4. **`.jar` file (Java ARchive)** — once you have one or more `.class` files (plus any other resources your app needs), they get compressed and bundled together into a single `.jar` file — this is the packaged, shareable, runnable form of your whole application.

**Simple analogy:** think of `.java` as a recipe written in plain English, `.class` as that recipe translated into a standardized shorthand that only a specific kitchen (the JVM) can read, and `.jar` as the fully packaged meal-kit box containing everything needed to actually make and serve the dish.

## Why compiled/binary files should never go into Git

This is presented as a hard rule, not just a suggestion. Compiled `.class` files and packaged `.jar` files should **never** be committed to your Git repository. Here's why:

- **Bloats the repository** — binary files are typically much larger than the plain text source code that generated them, and Git isn't efficient at tracking changes *within* binary files the way it is with text.
- **Causes constant merge conflicts** — since binaries are regenerated slightly differently on every build (even from unchanged source), different developers' compiled outputs will constantly clash with each other in Git, even though the actual *source* hasn't meaningfully changed.
- **Hides meaningful changes during code review** — a reviewer looking at a diff wants to see what *source code* changed, not a wall of unreadable binary noise.
- **Defeats the purpose of version control** — Git is designed to track meaningful, human-authored changes over time; binaries generated by a build process aren't "authored," they're *derived*, and should be regenerated fresh by anyone who needs them.

## What SHOULD be tracked in Git instead

- Your raw, human-written `.java` source files.
- Declarative build descriptor files — most importantly, `pom.xml`.

**Why this is sufficient:** since `pom.xml` fully describes how to build the project (dependencies, plugins, Java version, etc.), anyone — a teammate, or an automated CI server — can take just the source code + pom.xml and **deterministically** (meaning: reliably, the same way every time) reproduce the exact same compiled output themselves, without ever needing the binary files to be stored in Git in the first place.

## How this connects to what you've already set up

This is exactly why your `.gitignore` file excludes `target/` (where Maven puts all its compiled `.class` files and packaged `.jar` output) — you were already following this principle correctly, even before this lecture explained the full reasoning behind it.
