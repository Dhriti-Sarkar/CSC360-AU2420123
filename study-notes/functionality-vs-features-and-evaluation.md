# Functionality vs Features & Project Evaluation (explained simply)

From the mock presentations at the start of the session: a few groups presented live while the faculty and class gave feedback.

## The distinction

| | Functionality | Features |
|---|---|---|
| Meaning | What the software *does*: does it work correctly and fulfil its core purpose? | The extras built on top |
| Evaluation weight | **Higher** | Lower |
| Failure looks like | The core flow is broken or unreliable | Extras are missing |

A project that does fewer things reliably is judged more favourably than one with many features that are poorly implemented or break during the demo.

## Applied to the list matching project

- **Functionality:** correctly finding the common elements of the two lists and drawing the right arrows ([list-matching-project-overview](list-matching-project-overview.md)).
- **Features:** theme toggle, drag-and-drop, splash screen, UI polish ([javafx-theming-and-drag-and-drop](javafx-theming-and-drag-and-drop.md), [javafx-preloader-splash-screen](javafx-preloader-splash-screen.md)).

Make sure the first is solid before spending time on the second.

## Presentation flow

- Don't just demo features in sequence; communicate what the project is and why.
- Know what the evaluation actually expects rather than what you assume.
- Rehearse so the demo does not break live; test on the presenting machine.
- Good documentation ([readme-vs-wiki-documentation](readme-vs-wiki-documentation.md)) lets an evaluator understand the project without reading source and gives you control over how it is presented.

## Key takeaway
> Evaluation rewards a project that works correctly over one that merely has more on its feature list. Get the core right first, then add extras.
